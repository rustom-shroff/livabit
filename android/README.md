From the project root, after the existing build-tool setup and SDK acceptance, use the following fresh-start procedure. If the dedicated emulator is already running, the startup script refuses its occupied ports instead of terminating it. An existing owned emulator may be reused only when its startup record is fresh and all harness identity checks pass; otherwise close that owned emulator and start it afresh.

```powershell
.\scripts\setup-android-emulator.ps1
.\scripts\start-android-emulator.ps1
$taskAdb = Join-Path (Get-Location) 'artifacts\android-sdk\platform-tools\adb.exe'

# Wait for the owned emulator to boot; see the bounded readiness procedure in the plan.
$taskAvd = @(& $taskAdb -s emulator-5580 emu avd name)
if ($LASTEXITCODE -ne 0 -or $taskAvd[0].Trim() -ne 'liveabit-api35-test') { throw 'Unexpected emulator identity.' }
if ((& $taskAdb -s emulator-5580 shell getprop sys.boot_completed).Trim() -ne '1') { throw 'Emulator is not ready.' }
try {
    & $taskAdb -s emulator-5580 install -r .\artifacts\android-local-inspector\liveabit-local-inspector-0.2.4.apk
    if ($LASTEXITCODE -ne 0) { throw 'Inspector installation failed.' }
    & $taskAdb -s emulator-5580 install -r .\artifacts\android-local-inspector\liveabit-lifecycle-fixture-0.1.0.apk
    if ($LASTEXITCODE -ne 0) { throw 'Fixture installation failed.' }
    node .\scripts\test-android-emulator.mjs --serial emulator-5580 --expected-avd liveabit-api35-test --idle-ms 30000 --timeout-minutes 90
    if ($LASTEXITCODE -ne 0) { throw 'Read the recorded runtime failure before proceeding.' }
} finally {
    & $taskAdb -s emulator-5580 emu kill
}
```

Use this only for the dedicated project AVD. Startup resets its synthetic guest data, and the suite clears only its two owned test apps. It checks stopped/empty startup, consent and permission boundaries, selected-source reads, idle and screen-handoff comparisons, reset/restart and revocation controls. Secure-window UI hierarchy snapshots provide its visible assertions. Read the recorded result and each case after the run; a deadline expiry is not a completed workflow. These emulator observations do not establish physical-phone accuracy, source completeness or production OAP readiness. 1. Install the fixture APK when ready for a controlled trial. In the inspector, Stop and select only `org.liveabit.fixture`, then Start a fresh local session.
2. Open **liveabit Lifecycle fixture** and tap **Begin**. Leave it idle for approximately 30 seconds, then tap **Finish**. This creates an interior measurement window, excluding setup/return time.
3. Note the finished fixture's start time code, end time code and callback duration in milliseconds. These are synthetic test values, not another app's private activity. Begin/Finish markers use the fixture's own known resumed state; the inspector gets no corresponding production coverage guarantee.
4. Return to the inspector and tap **Inspect now**. Open its optional controlled-test comparison and manually enter those three values. The panel uses already retained estimates only; it makes no additional Android query. Inputs clear when you leave or reset the session.
5. Compare the sum of retained inferred intervals in the fixture window with the entered callback duration and signed difference. Read any discarded-estimate warning and ambiguity reasons: the sum can omit part of the controlled window. Unknown or conflicting evidence stays labelled. A zero difference is not an accuracy pass, and there is no automatic threshold. **Show fixture timing details** optionally reveals already retained fixture time codes, interval boundaries and session/report clocks for a controlled diagnosis. It labels all/latest counts and the exclusive wall-only query cursor; leaving or resetting hides and erases the panel. Record only an owned controlled timeline plus exact builds/API/OEM if a measurement is needed.
6. Repeat with several **Switch screen** actions between Begin and Finish. Both screens belong to the same package. Genuine handoff gaps remain excluded rather than being joined into a continuous session.
7. Stop/clear the inspector and Clear the fixture. A fixture run is limited to ten minutes/128 callbacks; malformed sequencing, clock changes, overflow or process restart invalidate or erase it.

The fixture observes its own callbacks, while the inspector reads Android's separate usage-history source. This comparison cannot certify other apps, missing-source completeness, background collection, battery use or OAP publication.
