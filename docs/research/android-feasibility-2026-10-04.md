# Android feasibility refresh

Research date: 2026-10-04. Status: documented feasibility and proposed measurement work; no Android application, SDK installation, device measurement or distribution approval is claimed.

The user's updated priority accepts the Windows reference evidence for proceeding and puts Linux extensibility on hold. Android feasibility and direct existing-agent integration can now advance in parallel. Research and an isolated collector measurement spike do not depend on Linux or a completed M2 integration. The full Android product still needs a verified direct M2 path. See the [roadmap](../project-roadmap.md), [measurement plan](../android-feasibility-plan.md), [OAP contract](../../specs/protocol/oap.md) and [direct-host research](direct-host-follow-up-2026-10-04.md).

## Verdict

**A consented, retrospective Android foreground-duration collector is a credible candidate. Its accuracy and useful coverage remain unmeasured.** The first candidate should use Android 15/API 35 or later, explicit package filtering, device-local aggregation and bounded background work. It can operate without a liveabit delivery service. Timely, complete collection on every OEM and continuous delivery cannot be promised. An app still needs a compatible final receiver in the user's chosen agent infrastructure; Android HTTPS support does not establish that host path.

The most consequential uncertainty is reconstructing package durations using permitted fields alone. Missing transitions, multiple activities of one package, process death and late OS persistence can make an apparently successful query incomplete. The spike must distinguish reliable segments from unknown time and establish a supported configuration matrix before claiming Android data quality.

## Collection API choice

`UsageStatsManager` needs the manifest declaration `PACKAGE_USAGE_STATS` and a separate Settings grant. Its event history has only a short, unspecified retention period. Queries can return null before the user has unlocked after reboot. Existing `queryUsageStats` buckets can extend beyond requested boundaries, so they are unsuitable for inventing precise 15-minute or post-consent totals. [UsageStatsManager](https://developer.android.com/reference/android/app/usage/UsageStatsManager)

Use `queryEvents(UsageEventsQuery)` on API 35+, with an explicit nonempty approved-package list and selected event types. Omitting package filtering requests all packages; an empty effective OAP allowlist must therefore stop collection before constructing the query. [UsageEventsQuery.Builder](https://developer.android.com/reference/android/app/usage/UsageEventsQuery.Builder)

Candidate inputs are package identity, event timestamp and `ACTIVITY_RESUMED`/`ACTIVITY_PAUSED`; `ACTIVITY_STOPPED` may help identify inconsistent sequences but denotes visibility, not a replacement foreground metric. The public event reference describes transitions per activity but provides no documented public activity-instance identifier getter. Do not read class names, interaction extras, shortcuts or notification contents to compensate. Package-only reconstruction is an engineering hypothesis, not a proven algorithm. Shutdown timestamps are persistence boundaries, and unmatched open sessions around shutdown/startup have unknown end times. [UsageEvents.Event](https://developer.android.com/reference/android/app/usage/UsageEvents.Event)

Foreground, visible and foreground-service durations are distinct. API 29+ multi-window can keep several activities resumed simultaneously. Compute the union within each app, permit overlap across apps, and never normalize the app sum into exclusive screen time or attention. [UsageStats metrics](https://developer.android.com/reference/android/app/usage/UsageStats), [multi-resume](https://developer.android.com/develop/ui/views/layout/support-multi-window-mode#multi-resume)

The current reference also documents `queryAppUsageDuration` at version **37.2**, requiring `QUERY_APP_USAGE`, with expanded calendar-aligned buckets. This is not an API 37 baseline assumption or a selected OAP collector. Its documented daily/weekly/monthly/yearly interval choices do not provide the required clipping semantics. Recheck actual SDK/device availability before any future evaluation. [New query](https://developer.android.com/reference/android/app/usage/UsageStatsManager#queryAppUsageDuration(android.app.usage.AppUsageDurationQuery)), [interval choices](https://developer.android.com/reference/android/app/usage/AppUsageDurationQuery#getIntervalType())

Older Android support is deferred, rather than silently using a broader collector. A later API 29–34 experiment could immediately redact the older event query in memory, but needs a separate privacy and device-quality assessment. Initially cover the app's installed personal profile only; work profiles, secondary users, Private Space and cross-profile attribution are unverified.

## Consent, time and honest coverage

Opening `ACTION_USAGE_ACCESS_SETTINGS` returns no grant result and may have no matching activity. Check effective usage access after returning and at every collection/send boundary. Use the applicable `AppOpsManager` APIs for the app's own UID/package; current documentation deprecates the unsafe checks at API 36. Denied, default/unknown or failed access must not become measured zero. [Settings action](https://developer.android.com/reference/android/provider/Settings#ACTION_USAGE_ACCESS_SETTINGS), [AppOpsManager](https://developer.android.com/reference/android/app/AppOpsManager)

The OS permission and each recipient's OAP grant remain separate. A local transaction records monitoring off, pause, narrowing or revoke before success is shown. Workers re-read the durable generation, scope, expiry and protected destination immediately before reads and network writes. Cancellation of queued work is useful cleanup, but the consent fence is authoritative. Offline revoke does not await the host. Already-started requests and already-received copies remain disclosed limits. [OAP authorization](../../specs/protocol/authorization.md), [privacy/security](../../specs/privacy-security.md)

Never query unauthorized pre-consent history to establish a starting state. Clip genuinely known segments to half-open window and grant boundaries; discard inseparable buckets and uncertain open segments. Coverage is observability of the whole approved scope, not the presence of an API response or an inventory of denied apps. If one approved app's state is unknown, conservatively reduce common coverage and corresponding durations. No coverage or no positive usage suppresses the whole group. Use only the existing reasons `consent_boundary`, `permission_missing`, `source_unavailable` and `clock_discontinuity`; do not invent a new wire reason. [OAP duration and coverage rules](../../specs/protocol/oap.md)

Use UTC wall timestamps for OAP and `SystemClock.elapsedRealtime()` for elapsed timing and budgets; it includes deep sleep. Detect divergence and reboot/process uncertainty conservatively. Android's network-time clock documentation explicitly warns against using it for security, so it is not an expiry-trust shortcut. [SystemClock](https://developer.android.com/reference/android/os/SystemClock)

## Background execution and reliability

Periodic WorkManager has a 15-minute minimum, while constraints and system scheduling can delay or skip a run. Expedited work also has quotas. These are scheduling opportunities, not a 15-minute collection or delivery guarantee. [Work requests](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)

Doze/App Standby restrict network and background execution. Android 16 applies job runtime quotas even when jobs execute with a foreground service. Android 15 limits background `dataSync` foreground-service time; a permanent service is not the baseline solution. Force-stop should be respected until user interaction removes the stopped state. Android 17 adds memory-limit behavior that also needs testing. [Doze](https://developer.android.com/training/monitoring-device-state/doze-standby), [job quotas](https://developer.android.com/about/versions/16/behavior-changes-all), [service timeout](https://developer.android.com/develop/background-work/services/fgs/timeout), [stopped state](https://developer.android.com/about/versions/15/behavior-changes-all), [Android 17 changes](https://developer.android.com/about/versions/17/behavior-changes-all)

Prefer a short periodic collector, foreground resumption and bounded connected-network drain opportunities. Store minimal checkpoint/outbox state locally, preserve immutable event bytes and original deadlines, and route all retries through OAP's persisted attempt/rate/backpressure limits. WorkManager restarts or library retries cannot open an unbudgeted cycle. Collection can continue locally during network loss when its own authority remains valid; network availability is not a collection prerequisite.

## Storage and direct network security

Room is a candidate transactional store for grants, checkpoints, recipient outboxes and budget state; using Room alone does not encrypt a database or prove revocation races. Keep state in app-private credential-encrypted storage and do no pre-first-unlock collection or delivery. Ordinary screen locking after first unlock differs from the reboot Direct Boot boundary. [Room](https://developer.android.com/training/data-storage/room), [Direct Boot](https://developer.android.com/privacy-and-security/direct-boot)

Android Keystore stores cryptographic keys rather than arbitrary bearer-token strings. Proposed storage encrypts credentials with a Keystore AES-GCM key, decrypting only for authorized requests. Inspect `KeyInfo` to report actual hardware protection; StrongBox is optional, and an app/process compromise may still use keys or observe a decrypted token. Per-use authentication would impede unattended delivery and must be a deliberate supported-mode choice. [Keystore](https://developer.android.com/privacy-and-security/keystore)

Exclude consent, credentials, checkpoints, outboxes and diagnostics from cloud backup, device transfer and applicable cross-platform transfer. `allowBackup=false` alone has OEM-dependent device-transfer limits. A restored or undecryptable state must start denied and require fresh pairing instead of reviving an old grant. [Backup/transfer rules](https://developer.android.com/identity/data/autobackup)

Android TLS supports a direct HTTPS client, but the adapter still has to implement the agreed destination policy: public-address classification for the cloud profile; exact approved address/CA or key trust for local TLS; hostname verification; TLS 1.2+; all redirects rejected; route/peer binding before credentials; bounded bodies/timeouts; no hidden retries, alternate proxies or background replays. Keep a token-free fingerprint of endpoint/profile/trust metadata, require fresh approval for changes, and permit credential rotation only within that approved destination. HTTP-client selection must prove these controls before carrying real usage. [Direct profiles](../../specs/protocol/profiles/direct-https.md), [Android network security](https://developer.android.com/privacy-and-security/security-config)

For target API 37, a LAN profile requires `ACCESS_LOCAL_NETWORK` unless an eligible system-mediated picker grants access to the selected device. That permission does not replace TLS or OAP pairing. Do not request LAN access for a public-HTTPS-only setup. Android 17's implicit localhost configuration can allow cleartext and bypass pinning, so enforce OAP HTTPS/trust explicitly at the adapter and configuration layers. [LAN permission](https://developer.android.com/privacy-and-security/local-network-permission), [localhost defaults](https://developer.android.com/privacy-and-security/security-config)

## Distribution and permission scope

Proposed manifest scope is usage access, `INTERNET` and `ACCESS_NETWORK_STATE`, plus only the permissions actually required by chosen scheduling libraries. Local-network permission is conditional on a selected LAN profile and target/API level. No Accessibility service, notification listener, VPN, screen capture, exact alarm, battery-exemption request, device/profile owner, enforcement capability or `QUERY_ALL_PACKAGES` is selected. Package identities are sufficient without labels; any later app selector needs its own finite visibility and disclosure review.

Play treats app inventory and sensitive usage-related data cautiously. Provide an in-app explanation and affirmative consent before access; disclose recipient transfer, background collection and retention. Audit Data safety against the actual implementation, even if direct user-directed transfer has a sharing exception. Keep analytics/crash-upload SDKs out of the spike. Policy documentation is not evidence of approval for this particular app. [User Data policy](https://support.google.com/googleplay/android-developer/answer/10144311?hl=en), [sensitive APIs/package visibility](https://support.google.com/googleplay/android-developer/answer/16558241?hl=en), [Data safety](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en)

The current Play floor for new phone apps/updates is API 36 from 2026-08-31. API 37 is documented for Android 17; compile/target 37 is the proposed spike choice, with exact compatible toolchain versions pinned at setup. Distribution also needs a refreshed developer-verification assessment: current protections began in selected regions/stores on 2026-09-30, and a free limited-distribution path covers up to 20 explicitly authorized devices. Neither distribution nor registration is performed here. [Play target requirements](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en), [Android 17 SDK](https://developer.android.com/about/versions/17/setup-sdk), [developer verification](https://developer.android.com/developer-verification), [limited distribution](https://developer.android.com/developer-verification/guides/limited-distribution)

## Observed local readiness

Read-only inventory on the Windows workspace found no `adb`, emulator, `sdkmanager`, Java/Javac, Gradle or Android Studio in PATH or their standard SDK/Studio/JDK/cache locations. `ANDROID_HOME`, `ANDROID_SDK_ROOT`, `JAVA_HOME` and `GRADLE_HOME` are unset. This does not exclude a custom installation elsewhere. No `adb` was available, so no connected-device query was made. No SDK, OS feature, app, emulator, developer account or device permission was installed or changed.

The next deliverable is the [measurement spike](../android-feasibility-plan.md): prove permitted event reconstruction and local controls first, then test synthetic direct TLS separately. A collector result can inform Android feasibility while M2 remains unproven; it cannot establish agent integration, production Android support or M3 completion.
