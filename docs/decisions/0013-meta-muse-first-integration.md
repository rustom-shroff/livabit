# ADR-0013: Prioritize Meta Muse and protected local connection setup

Date: **2026-10-08**. Status: **accepted by the user's explicit instruction to develop the Meta Muse integration and continue independently with protected local connection setup**.

The first existing-agent target is now **Meta Muse**, replacing the Grok Bot priority in [ADR-0011](0011-grok-bot-first-integration.md) and its webhook route in [ADR-0012](0012-grok-bot-direct-webhook-priority.md). Preserve those decisions, research, synthetic probes, tests and review artifacts as historical work. Retain the ChatGPT dots research as well. No existing evidence is relabeled as Muse behavior.

The [Muse feasibility follow-up](../research/meta-muse-webhook-feasibility-2026-10-08.md) records the official free offering with usage limits. Free availability is not unlimited usage or proof of account eligibility. The user's report that Muse supports webhooks selects the investigation and development direction; it does not establish a device-originated receiving endpoint, authentication method, request schema, acknowledgement meaning or retry contract. Those Muse-specific facts and actual account access remain unverified.

Proceed independently with host-neutral protected local setup and isolated transport groundwork. Keep setup credentials and exact destination details local, out of chat, source, command-line arguments and evidence logs. Synthetic tests may use an owned final TLS mock. Such tests prove local controls only, not a Muse integration. Do not transfer Grok's bearer header, JSON POST or HTTP 200/run-start classification to Muse without a verified Muse contract. No live Muse send or selectable production profile is enabled by this decision alone.

Before a real synthetic pilot, establish a supported inbound path to the user's existing Muse agent, exact provider-owned destination and recipient, native credential scope/lifetime/revocation, request and response limits, and receipt/replay semantics. Review any differences from the agreed OAP capability, admission and consumption contracts before integrating the production publisher. A transport acknowledgement, routine start or natural-language Skill response is not a valid OAP consumption receipt or deterministic durable deduplication. See [AC-22/23/24/29](../../specs/acceptance-criteria.md); AC-28 remains conditional on selecting an MCP profile.

Activity must travel directly from its producing device to the chosen agent's existing infrastructure. No project hosting, proxy, tunnel, mailbox, desktop forwarder or required user-operated bridge is introduced. An unsupported Muse path remains unavailable; no paid API replacement agent, purchase, plan upgrade or on-demand spending substitutes for the requested free target.

The accepted collector baseline, deferred precise-duration/complete-coverage investigation and Linux hold remain. Unknown coverage stays unknown. The Android inspector and its tested APKs remain local-only and unchanged. Any changed APK proposed for a phone trial still needs emulator validation of its exact bytes. M2/M3 remain unproven until their actual evidence gates pass.

## Account investigation follow-up, 2026-10-08

No further login, approval or phone accuracy trial resolves that platform gap.
