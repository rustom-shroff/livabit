Date: **2026-10-15**. Status: **final host verified and currently healthy; Android exact-APK and warm-host observation gates passed; cold-start readiness defect remains open**. This review extends, rather than replaces, the [October 14 foundation review](personal-agent-foundation-2026-10-14.md). The accepted direction is [ADR-0025](../decisions/0025-durable-activity-analysis.md); requirements and acceptance are in the [PA specification](../../specs/personal-agent-intervention.md). ## Problem and resulting design

Activity receipt previously requested model execution through a native hook for each eligible packet and copied context into ordinary main chat. A committed observation alone could outlive failed post-admission reasoning without a durable recovery obligation. The phone expected run admission, not independently durable receipt. A disconnected companion caused a pre-invocation failure without a waiting delivery intent.

The new source adds an authenticated receipt endpoint that atomically stores an observation/review obligation, a bounded leased/coalescing worker, an isolated activity session belonging to the same main personal agent, a limited ordinary-chat evidence/feedback bridge and bounded pre-dispatch notification recovery. The sender candidate supports the new truthful receipt while retaining the old hook. No third-party messaging, extra connector or separate service is introduced.

The conversation guidance now supports optional intent/feelings inquiry, current goals and circumstances, deliberate leisure, practical alternatives and reconsideration after repeated attempts. A meaningful growing conversation is a product aim. No fixed diagnosis, emotional taxonomy, tone escalation or automatic accountability email is enabled. The [15-case evaluation plan](../evaluation/personal-agent-conversation.md) distinguishes review criteria from empirical results.

## Independent review and corrected failure cases

Independent review identified three gaps worth retaining as regression cases:

1. A native run could call a decision tool before the admission response had attached its run ID to a job. A lost admission response created the same gap. The installed tool factory also omits run ID. The new binding uses authoritative before/after-tool-call hook identities and checks active job/deadline for every activity tool, failing closed for missing/stale bindings. Review retry reuses the original decision even when `eventId` is omitted; model arguments cannot provide its review identity.
2. Superseding or cancelling only `queued` notification intent left an older `checking` intent awaiting inventory able to send after newer advice or an observed opt-out. Supersession/revocation now also fences unreserved checking intent; existing native reservations remain governed by the one-attempt ledger. Deferred-inventory regressions cover both races.
3. A duplicate recorded decision did not prove its notification had ever been requested. Guidance that categorically forbade delivery on `duplicate:true` could lose a prompt after a crash between record and notify. Recovery now distinguishes decision, intent and native attempt, reuses the original ID and lets the idempotent delivery tool enforce existing queued/suppressed/uncertain outcomes. This does not authorize a replacement decision or blind resend.

These cases test dependable mechanics around the model's choices. They do not prescribe which psychological approach is correct for a particular person.

Review also identified that a one-job queue alone did not bound a chain of model-requested reviews. The source now limits these to three since fresh accepted activity or a deliberately linked main-chat user report, with one idempotent scheduling request per recorded review. Duplicate packets do not reset it. This is a resource bound, not a clinical dose, attempt threshold or pressure ladder.

The advisory reconsideration cue also previously treated any historic benefit as a permanent reason not to mark repeated attempts. It now counts support decisions after the latest supported benefit report while preserving lifetime/native-attempt counts and explicit same-millisecond ordering ambiguity. Two new regressions cover old benefit followed by later attempts outside the displayed narrative, benefit reset, and timestamp ties. The focused evidence/delivery suite passed **35 tests** after this change. No schema or original timestamp was rewritten.

Final audit found one more diagnostic distinction: successful native run completion did not prove a structured decision was recorded. The worker now checks the exact review binding and stores `completed_without_decision` plus `decision_recorded:false` when absent, while still settling the completed work. It does not infer silence, fabricate a no-intervention choice or retry indefinitely. Two cases passed for missing decision versus explicit recorded `no_intervention`, including reopening the database, and are included in the final aggregate run and verified final installed source. A real native scheduled model run was not requested by verification.

Final review also separated factual event identity from reasoning-operation identity. A fresh trusted reply/follow-up review can now choose another approach citing the same window; retrying that review still returns its original choice. Legacy event deduplication and foreign-owner guards remain. A linked main report atomically retires old unreserved queued/checking prompts before scheduling reconsideration, with reserved possible native effects left to their one-attempt ledger. The **84-case focused analysis/conversation/delivery/evidence run passed**, including two new integration/rollback cases, also included in the final aggregate run and verified final installed source. A failed review write cannot leave a saved report or a half-cancelled prompt.

## Separate desktop availability finding

During native preflight, the managed gateway was stopped. Startup failed on an ownership lock after roughly five minutes. Read-only inspection found that the recorded gateway owner PID now belonged to an unrelated process created later: the PID had been reused. Both the current owner projection and historical gateway-state projection retained stale ownership facts.

The operator checked that no owned gateway process remained, preserved the exact stale files by renaming them to backups in their existing private host directories, and restarted the managed gateway. The managed runtime subsequently reported **running**, and a warmed gateway later passed the native HTTP checks below. Lock recovery itself changed no phone app, database content or native application code; the subsequent plugin deployment is a separate action.

This establishes a desktop availability problem independent of the companion's Android background behavior. It does not prove that the phone was off, the app was absent, its service was stopped, or that this was the sole cause of earlier missing notifications. Private account paths, node identities, tokens, tasks, messages and activity contents are intentionally omitted from this report.

A separate native cold-start delay remains. Earlier restarts took roughly nine minutes before becoming responsive; the final restart still took about seven minutes from process birth to first observed health. These timings and profiles were observed during concurrent development/emulator work, not an isolated idle A/B benchmark; they do not establish a universal startup time or one component's sole cause. The full cause is **unattributed**. A `memory-core-dreaming` startup-phase label spans an awaited cron reconciliation and process-wide CPU; it does not establish that dreaming or a model sweep caused the stall. No native OpenClaw code fix, memory disabling or automatic removal of lock files is claimed. While the gateway is unavailable, receipt and workers cannot provide live service. TASK-PA-010 tracks reproduction under controlled conditions; no further restart was made merely for profiling.

An actual warmed native CPU capture lasted **7.084 seconds** with **540 samples**. It attributed **2.603 seconds (36.75%) inclusive** to Windows foreign-owner process-birth checks reached through file-lock stale-owner handling and synchronous process spawning. Installed code can perform uncached PowerShell/WMIC fallbacks with a combined timeout up to roughly ten seconds; inability to read a protected process's birth time remains uncertainty, not authority to remove its lock. This identifies measured synchronous work, not proof that it explains the entire startup delay.

The operator separately verified another stale artifact: the native WhatsApp **credential-lock sidecar**, whose recorded owner birth preceded the unrelated process currently using that PID. Its checked preservation succeeded at **3:02:45 p.m. America/Chicago (20:02:45 UTC)** during the authorized stopped-host transition. A private maintenance copy of the installation helper verified owned root/child processes absent, port closed, exact path/hash and the reused PID's current birth before preserving that one sidecar. The committed helper, credential contents, account linkage and unrelated process were unchanged. This was a one-time recovery of **three separately verified stale artifacts** across the session. Subsequent known-lock inspection found one valid live gateway owner and no other stale generic owners in the inspected locations. This is not automatic lock removal or a systemic upstream fix.

Post-maintenance profiling captured **7.129 seconds and 518 samples**, with 0.6% idle and no earlier foreign-lock hotspot. Current sampled work included module evaluation/configuration-schema loading and profiler initialization; inclusive frames overlap and must not be added as independent shares. This does not sample the entire seven-minute cold-start interval. The later warm native checks passed, but the controller's readiness timeout and slow cold startup remain unresolved.

The synchronous native Windows owner-birth lookup remains an upstream availability concern. One-time sidecar recovery removes the proved stale artifacts; it does not make process inspection nonblocking, resolve unknown protected-process identities, or establish that another lock cannot cause delay later. No external issue or message was posted by this work.
