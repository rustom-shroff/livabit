The [offline routine admission model](integration-drafts/grok-bot-local-admission.md) remains a separately recorded local component. A trusted local driver pre-provisions an exact synthetic binding with the existing receiver; the model reuses its raw JSON validation and transactional duplicate/page ledger without an HTTP server. A separate inspection operation projects fresh owned observations, authenticates the binding again after reading durable state and preserves original event time, coverage, page identity and gaps. This narrower fixture capability refuses application labels and any extensions member, allowing full event reconstruction and comparison against the original stored ledger digest; no OAP schema or contract is changed. Its [separate review](review/grok-bot-local-admission-2026-10-08.md) records fixture admission and storage evidence only: native raw body, trusted invocation mapping, actual host persistence and separate concurrent routine processes remain unverified. It admits only `test.app` namespaces, offers no model/Skill callback and is neither a deployable Grok receiver nor a forwarding service.

The [offline delivery journal](integration-drafts/grok-bot-delivery-journal.md) is the next separate local component. It retains bounded immutable authored pages and original deadlines, commits a single irreversible reservation and rolling-hour recipient budget before exposing a local fixture handle, and never reissues a handle after restart. At most one unfinished reservation is allowed; an unfinished reservation remains side-effect-unknown and blocked. Every observed outcome is terminal, including body-not-submitted, with no retry or restaging. Original expiry or revocation removes page bodies while bounded tombstones prevent reused identities; capacity fails closed rather than evicting accounting. Local pause/revoke state and generation determine consent at outcome recording, while an already in-flight remote side effect cannot be undone. The [journal review](review/grok-bot-delivery-journal-2026-10-08.md) records synthetic local results only, with no actual native HTTP response, valid host consumption or evaluation.

The journal performs no network, account, server or forwarding operation and has no connection to the retained probe. That probe generates its own page internally and has no durable pre-body reservation interface; journal evidence does not harden or wrap its existing native attempt. This conservative offline policy neither registers a native publisher profile nor amends OAP delivery semantics. It supports one owning process/store instance; restart/file reopen is not power-loss assurance because Windows `JsonStore` lacks directory fsync. Real native integration still needs a reviewed immutable-page/pre-body mapping, trusted routine admission and account evidence.

The new [offline journaled synthetic sender](integration-drafts/grok-bot-journaled-sender.md) composes the unchanged journal and admission model using distinct owned transactional stores and a module-owned virtual wire. It begins possible fixture body submission only inside the journal store's `afterCommit`, after its reservation and budget persist under the same-instance lock. Trusted clock, original expiry, durable local state/generation and a synchronous invalidation epoch fence submission. Pause, revoke or disposal requests invalidate unfinished authority before awaiting persistence; resume cannot revive an earlier attempt. The exact canonical journal page reaches the local receiver without a replacement event or automatic retry. The [sender review](review/grok-bot-journaled-sender-2026-10-08.md) distinguishes fixed modeled HTTP acceptance, durable local admission and response uncertainty from actual native receipt/evaluation. There is no arbitrary callback, endpoint, account, network, forwarding service or automatic Skill invocation. The retained native probe remains unchanged and unconnected; independent file-sharing routine processes and power-loss durability remain unsupported.

The current reference adapter implements only the agreed direct profiles. Its `deliver` interface returns `ValidConsumptionReceipt`; publisher success records both receipt and consumption. Production approval requires authenticated OAP capabilities, known finite credential expiry, receiver-enforced admission, and the specified durable `200` receipt. A generic provider API cannot be placed behind that interface by returning an invented receipt. [Direct profile](../specs/protocol/profiles/direct-https.md), [interfaces](../specs/protocol/interfaces.ts), [authorization](../specs/protocol/authorization.md)

**No researched provider-native adapter is ready to implement unchanged against those executable contracts.** A native adapter needs an explicitly reviewed profile addition and, where receipt semantics differ, a delivery-result/interface amendment. An actual existing runtime implementing the agreed OAP receiving interface could use `direct-local-tls-v1` without relaxing its contract; none has been identified or verified.

## Synthetic fixture and real-host observation matrix

| Case | Required outcome / observation |
| --- | --- |
| Arrival and recipient | Exact immutable event reaches only the selected existing agent. Native acknowledgement is classified accurately; unrelated recipients and conversations are untouched. |
| Lost acknowledgement / retry | Same ID/body/key reused within bounded attempts; unknown outcomes remain unknown. Observe native dedupe; never issue a fresh ID to bypass uncertainty. |
| Changed body / duplicate | Conflicting ID/body is rejected locally before send; verify receiver/native handling where supported. If native retention cannot cover OAP recovery, record the gap and do not claim exactly-once consumption. |
| Delayed / out of order | Old events cannot replace current activity; gaps and expiry remain visible. A successful host run on an old event is not a current-usage signal. |
| Partial group | Missing pages stay unknown; interpretation waits for required completeness or states its limitations. Verify that host batching/conversation continuity does not merge distinct scopes/windows. |
| Expired or wrong credential | No data sent after local expiry or to an unpaired origin/path. Native auth denial requires attention; no alternate credentials or recipient fallback. |
| Rotation / narrowing | Old token and old scope cannot authorize later sends; old pending payloads are purged on narrowing. Prove receiver-native rejection if promised by the selected profile, otherwise disclose the mismatch. |
| Offline pause / revoke | Local denying commit succeeds without network; no new dispatch or retained-history read begins after it. Already dispatched activity may arrive; remote deletion is not claimed. |
| Rate / oversized / malformed response | Local page, fresh-event, retry, byte, retention and backpressure budgets still govern. No provider batching, HTTP library replay or status polling bypass. Native success with bad response shape stays ambiguous. |
| Appropriate response / silence | Existing standing instructions decide whether to respond, suggest an alternative, or remain silent. Missing context is acknowledged; absent activity is not zero; duration is not automatically harmful use. |
| Prompt injection | Labels, extension values and native input data cannot widen authority, redirect delivery, override instructions or trigger device actions. The liveabit Skill supplies no collection permission. |
| Privacy and topology | Only device and chosen agent infrastructure handle delivery/control, apart from reviewed provider authentication. Record host-side retention/logging/output behavior separately from local deletion. |

The liveabit Skill design can be prepared before account setup: validate data, maintain page/window uncertainty, respect original event age and agent-owned context, and follow the user's existing communication preferences.
