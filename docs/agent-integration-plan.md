# Existing-agent direct integration plan

Date: **2026-10-04**. Status: **prepared plan; host selection and real-account evidence pending**.

Priority update, 2026-10-05: [ADR-0009](decisions/0009-android-local-inspection-first.md) puts the native local collector and inspection trials first. Agent selection and activation are deferred until local findings; the earlier pending host-choice question is not a prerequisite for current work. This plan is retained for when integration resumes.

The user has reprioritized the work: existing Windows reference evidence is sufficient to proceed; Linux portability is on hold and is not claimed verified. Direct integration and Android feasibility are now the priorities. This plan does not amend the OAP wire contract or declare M2/Android complete. No real host is selected, no account has been supplied, and no pilot, new agent, live credential, or AI call has been made.

**Open Activity Protocol (OAP)** carries authorized activity. **liveabit Skill** supplies interpretation guidance inside the user's existing agent. The [strict capability catalog](agent-compatibility.json) separates documented primitives from proven full-path compatibility. Every production-selectable flag is currently false; this catalog is research data, not runtime destination configuration.

## Immediate deliverables and implementation boundary

Prepare the following without account access: the catalog, the exact profile-change proposals below, a synthetic host-envelope fixture matrix, a redacted pairing checklist, an observation template, and the liveabit Skill's host-neutral interpretation/evaluation design. These preparations do not need Linux or a real agent to begin. Executing a real-host pilot depends on the already-pending choice of an existing agent and its account eligibility; no additional choice request is introduced here.

The current reference adapter implements only the agreed direct profiles. Its `deliver` interface returns `ValidConsumptionReceipt`; publisher success records both receipt and consumption. Production approval requires authenticated OAP capabilities, known finite credential expiry, receiver-enforced admission, and the specified durable `200` receipt. A generic provider API cannot be placed behind that interface by returning an invented receipt. [Direct profile](../specs/protocol/profiles/direct-https.md), [interfaces](../specs/protocol/interfaces.ts), [authorization](../specs/protocol/authorization.md)

**No researched provider-native adapter is ready to implement unchanged against those executable contracts.** A native adapter needs an explicitly reviewed profile addition and, where receipt semantics differ, a delivery-result/interface amendment. An actual existing runtime implementing the agreed OAP receiving interface could use `direct-local-tls-v1` without relaxing its contract; none has been identified or verified.

## Exact profile-change proposals to prepare for review

These proposals identify changes needed before implementation. Names below are tentative identifiers, not enabled profiles. Keep `activity.summary` bodies, immutable window/page identity, local consent, scope, age/byte/rate/retry limits, and the no-intermediary requirement unchanged.

| Proposal | Required change and review surface | Required proof before approval |
| --- | --- | --- |
| CP-HOST-01: transport results | Add a separate tagged native result such as `receipt_only`/`queued` to the adapter contract; preserve `ValidConsumptionReceipt` for the existing direct profiles. Update delivery/status rules so native acknowledgement advances only transport receipt, never `last_valid_consumption_at`. Define whether an acknowledged event leaves the send outbox, what bounded metadata remains, and how unknown outcomes/late completion are represented. Update interfaces, status schema only if new fields are necessary, conformance and fixtures. | Native response schema and byte limits; restart-safe lost-ack handling; duplicate behavior; expiry/retention; no false consumed/evaluated/notified state. Do not weaken the current direct profile's H5 requirement. |
| CP-HOST-02: native authentication | Add an explicit host-native authentication policy under A5 and its profile, including A3's new-epoch receiver-admission requirement. Define actual receiver identity, user/workspace/agent authority, exact destination/path, credential storage, issued expiry, reissue/rotation, and revocation. Disclose any difference from device/recipient/scope-bound reference credentials and host rejection of old scope. | Actual issuer/account evidence; old credential rejection; sharing removal; whether a token can invoke unrelated agents; recipient/device isolation limitations. | CP-HOST-03: capability and pairing | Add each selected profile ID to the capability-schema enum and `DeliveryProfileId`, with bounded local pairing metadata and its actual discovery mechanism. No fallback to another host or forwarding service. |
| CP-HOST-04: OpenAI Events profile | Specify `openai-mcp-events-v1` only if chosen: pin `2026-07-28`; map one unchanged OAP page into the event `data` field; keep distinct native/OAP subscription identifiers; define filters, canonical arguments, callback verification/signatures, finite refresh, secret rotation, replay/gaps, unsubscribe, and same-device provider-owned control transport. The agreed capability enum and runtime publisher currently recognize only `direct-https-v1`, `direct-local-tls-v1`, and `direct-loopback-test-v1`. An optional MCP extension was anticipated by AC-28, but that does not approve an unspecified mapping. Approval must precede enabling native profile IDs or changing acknowledgement behavior; source/schema changes are outside this preparation task.

For Workspace Agents, official scoped-token examples include 7/30/60/90-day validity and require expiry. [Tokens](https://learn.chatgpt.com/docs/enterprise/access-tokens) The reference maximum is **30 days**, with known issuance/expiry and receiver-enforced device/recipient binding. A 7/30-day choice may satisfy lifetime only; a 60/90-day token does not become conforming by locally stopping early. The reviewed native token scope does not establish restriction to one device, recipient or OAP epoch. If those semantics cannot be supplied, CP-HOST-02 must disclose the exact difference and leave the reference profile intact. ## Synthetic fixture and real-host observation matrix

| Case | Required outcome / observation |
| --- | --- |
| Arrival and recipient | Exact immutable event reaches only the selected existing agent. Native acknowledgement is classified accurately; unrelated recipients and conversations are untouched. |
| Lost acknowledgement / retry | Same ID/body/key reused within bounded attempts; unknown outcomes remain unknown. Observe native dedupe; never issue a fresh ID to bypass uncertainty. |
| Changed body / duplicate | Conflicting ID/body is rejected locally before send; verify receiver/native handling where supported. If native retention cannot cover OAP recovery, record the gap and do not claim exactly-once consumption. |
| Delayed / out of order | Old events cannot replace current activity; gaps and expiry remain visible. A successful host run on an old event is not a current-usage signal. |
| Partial group | Missing pages stay unknown; interpretation waits for required completeness or states its limitations. Verify that host batching/conversation continuity does not merge distinct scopes/windows. |
| Expired or wrong credential | No data sent after local expiry or to an unpaired origin/path. Native auth denial requires attention; no alternate credentials or recipient fallback. |
| Rotation / narrowing | Old token and old scope cannot authorize later sends; old pending payloads are purged on narrowing. Prove receiver-native rejection if promised by the selected profile, otherwise disclose the mismatch. |
| Offline pause / revoke | Local denying commit succeeds without network; no new dispatch or retained-history read begins after it. Already dispatched activity may arrive; remote deletion is not claimed. |
| Rate / oversized / malformed response | Local page, fresh-event, retry, byte, retention and backpressure budgets still govern. No provider batching, HTTP library replay or status polling bypass. Native success with bad response shape stays ambiguous. |
| Appropriate response / silence | Existing standing instructions decide whether to respond, suggest an alternative, or remain silent. Missing context is acknowledged; absent activity is not zero; duration is not automatically harmful use. |
| Prompt injection | Labels, extension values and native input data cannot widen authority, redirect delivery, override instructions or trigger device actions. The liveabit Skill supplies no collection permission. |
| Privacy and topology | Only device and chosen agent infrastructure handle delivery/control, apart from reviewed provider authentication. Record host-side retention/logging/output behavior separately from local deletion. |

The liveabit Skill design can be prepared before selection: validate data, maintain page/window uncertainty, respect original event age and agent-owned context, and follow the user's existing communication preferences. Installation metadata and host-specific tool names wait for the selected profile. No reminder, notification promise, goal copy, device restriction, or new coach is implied by installing a skill.

## Android dependency and present blockers

Android feasibility work can proceed in parallel as preparation for consent, usage coverage, background delay, protected credential storage, local retention and offline revocation. Real production transport remains dependent on the selected profile. Workspace Agent HTTPS needs outbound opportunities; Events plus Tunnel additionally needs a supported device-local control client, its authentication and reconnection lifecycle. Neither path permits a hidden forwarding machine. Android delivery timing, battery, reboot, Doze and OEM behavior need their own observations; no guaranteed continuous delivery is inferred from an agent API.

The only account-dependent blocker now is the pending existing-host/account choice and its eligibility. The technical blockers are explicit profile/result/auth compatibility, native limits/dedupe proof, and the complete direct control/delivery path. Useful work before that choice is the CP-HOST review packet, native synthetic fixtures, host-neutral liveabit Skill evaluation cases, and Android feasibility measurements. Missing capability stays unavailable; it is not repaired by introducing intermediary infrastructure.
